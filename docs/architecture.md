# 架构约定

本文是两端共享的架构参考，规定边界与约束，不代表功能已实现。技术选型须区分已确定、候选和待设计。

## 仓库与依赖

- `tossy` 保存公开 Core、SDK、Desktop、CLI、协议和 Relay；`tossy-mobile` 保存私有移动应用与平台适配。
- 两个仓库独立提交和发布。公开仓库不得包含私有实现、签名材料或密钥。
- Desktop、Mobile、CLI 通过 Core SDK 访问业务能力。Core 不依赖 UI、MyGo 或私有移动端。
- 平台层负责权限、文件授权、通知、安全存储和生命周期适配，通过明确的接口向 Core 提供能力。
- 包按业务职责组织；接口由使用方按实际需求定义。采用显式依赖和组合，避免循环依赖及无实际用途的抽象层。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| Core / SDK | 统一生命周期；提供命令、查询、事件 |
| Identity | 设备身份、联系人、信任及密钥变更提示 |
| Messaging | 消息状态、确认、重试、去重及历史 |
| Group | 成员、权限及群密钥状态 |
| Transfer | 流式传输、进度、取消、续传及完整性 |
| Security | 成熟 E2EE 协议集成、身份验证及密钥生命周期 |
| Storage | 持久化、迁移及存储保护 |
| Discovery | 发现和更新地址，不决定信任 |
| Connection | 路径选择、超时、重连及故障转移 |
| Relay | 在线不透明流转发、授权及资源限制 |
| Protocol | 编码、版本协商、输入限制及兼容性 |

业务状态和持久化由 Core 管理；UI 展示状态并提交用户操作。文件由 Core 流式处理，UI 只传递文件访问能力与控制信息。

Relay 服务不得依赖聊天、群组、文件业务或业务解密逻辑；不保存聊天记录、文件或离线消息。离线暂存和推送属于后续独立能力。

## 网络与安全

- 默认连接顺序为 LAN → 可用且获授权的 Relay → WAN。实际建连失败后继续尝试其他候选路径。
- 发现、可达和可信分别判断；中继可达不代表目标可通过该中继连接。
- 所有业务路径保持 E2EE；连接加密不能代替消息、离线及群组安全设计。
- 首次信任、密钥变更、设备撤销和恢复必须有明确语义。先做威胁模型，再选择成熟密码协议与库。
- 对网络输入、目录清单及文件路径设置边界，防止重放、路径穿越、恶意符号链接、覆盖和资源耗尽。
- 日志不记录密钥、消息正文或文件内容；持久化、缓存与备份的保护方式需单独设计。

## 已定与待定

- 已定：Go Core、MyGo Native、双仓库边界、SDK 访问方式、默认连接顺序和 E2EE 要求。
- 待验证：MyGo 五平台及移动原生能力；go-libp2p、mDNS、QUIC/TCP、Circuit Relay v2。
- 待设计：多设备身份、E2EE 与群协议、消息投递语义、WAN 发现、数据库及存储加密、文件与续传协议。

候选方案不得直接作为生产架构落地。验证应记录目标、环境、结果和限制；移动原生能力需要真机证据。
