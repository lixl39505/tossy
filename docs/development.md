# 开发约定

本文是两端共享的开发参考。项目边界见 [架构约定](architecture.md)；通用 Go 写法遵循适用的已安装 Skill，不在此重复。

## 开始工作

- 先读目标仓库 `AGENTS.md`、共享参考和相关决策，再检查已有实现与调用方。
- 先明确目标、改动范围和验收方式；未定事项先设计验证，不用实现默认为其作出决策。
- 修改 Go 代码时使用 `go` 和 `use-modern-go`；按任务加载并发、安全、测试等专项 Skill。
- 已加载 Skill 引用直接相关但未安装的 Skill 时，说明名称和用途；未经用户要求不自动安装，不受影响的工作继续。

## 编程规则

- 使用简洁中文沟通、编写文档和注释；标识符、命令、协议字段及必要原文保留英文。注释解释约束和原因。
- 包名短且职责清晰。优先标准库、具体类型和小接口；不为未来需求引入通用框架。
- 依赖通过构造或参数显式传入，避免可变全局状态。新增依赖须说明用途、替代方案及许可影响。
- 错误补充操作上下文并保留错误链；在负责处理的边界记录一次日志。正常失败返回错误，不用 panic。
- 可能阻塞的操作支持 `context.Context`，由调用方传入；沿调用链传播取消和期限。
- 启动 Goroutine 时明确所有者、退出条件及等待方式；明确共享状态的同步方式和 Channel 的关闭方。
- 创建资源的一方负责释放；转移所有权时写明约定。取消、关闭和部分失败不得泄漏资源。
- 大文件使用流式 IO；队列、缓存、输入及重试设置上限，避免无限增长。

## SDK 与协议

- 命令说明返回代表受理还是完成；查询说明状态含义；事件说明顺序、缓冲、溢出和取消订阅行为。
- SDK 不暴露 UI 类型或网络库内部类型；不要假设事件回调位于 UI 线程。
- 修改 Core API 时检查 Desktop、CLI 和 Mobile 调用方；无法检查的调用方列为未验证项。
- 修改协议时说明版本协商、旧端行为、大小限制及错误响应，并验证兼容性。
- 持久化格式变更须说明迁移及失败恢复方式；避免静默破坏现有数据。

## 验证与交付

- Go 改动先格式化，在受影响模块执行 `go test ./...` 和 `go vet ./...`；并发改动在支持环境执行 `go test -race ./...`。
- 本地用根目录 `go.work` 联调；发布和 CI 对各模块分别执行 `GOWORK=off go test ./...`、`GOWORK=off go build ./...`，验证固定版本依赖。
- 测试覆盖外部行为和故障边界。协议、安全、状态与数据变更补充针对性用例；不为纯文档改动添加测试。
- 网络改动验证超时、重连及路径回退；文件改动验证完整性、取消、续传和目录安全；移动原生能力通过真机验证。
- 按风险使用 Fuzz、漏洞扫描及集成测试；依赖变更检查漏洞和许可。只报告实际执行的检查。
- 交付时说明改动、验证结果及剩余限制，同步受影响文档。仅提交本任务文件，两个仓库分别提交，按需更新 Workspace 子模块指针。
